# 0008: The app is the one `nod serve` serves

Status: accepted (2026-11-27), from the owner's second brainstorm ([concept](../concept.md), "Opening up", part D), written with #51; the details the brainstorm left open were decided in its spirit and are listed in the pull request. Replaces the concept's "Hosted on GitHub Pages … It talks to `nod serve` over loopback" and "The published CLI opens the web app of its own release channel" (Architecture, Web app; Release). Amends [ADR 0005](0005-named-host.md) §1 ("Loopback still serves no page"), §4 (the served web app is now loopback's too) and §7 (the hosted UI also forwards to this machine's app). Epic #50.

## Context

The dashboard ran in two places: the hosted UI (`ui.nod.frebreco.de`, stable or `/next`) paired with `nod serve` over loopback, and, since ADR 0005, the web app `nod serve` itself serves on a named host for a phone. The hosted UI follows its release channel, not the CLI that runs: an older `nod serve` and a newer page meet with "nod serve and this page do not match", a downgrade has no page at all, and Chrome's Local Network Access asks every user for a permission whose prompt reads "connect to any device on your local network" (finding 04, row 3). A browser tab is also not an app: no window of its own, no icon, nothing when the server is down.

The owner wants nod to "feel like a real app": installable, opening on its own, telling you how much needs you, and the page always the server's.

## Decision

1. **The installable app is the one `nod serve` serves on loopback**, at `http://127.0.0.1:<port>/` (`--port`, default 4518). Loopback is a secure context, so the page may install, register a service worker and use the badge. The page is the CLI's own build (`--web-dir`, default the package's `web/`, in a checkout `dist/web`; ADR 0005 §4), so **the UI always matches the server, a downgrade included**, and page and socket share one origin: no Local Network Access prompt, no CORS.
   - Served whenever there is a built web app: always for a release (the package ships it), in a checkout once `bun run build` has run. Without one, loopback serves no page, as before, and `--web-dir` naming a folder without an `index.html` stops with that message.
   - The same rules as the named host's page (`src/server/static-files.ts`): no path out of the root, `index.html` for every other path, no framing, no sniffing, no referrer; `/assets/` immutable, everything else `no-cache`.
   - The app's origin is let in on the loopback side next to the hosted UI's and the dev server's (`allowedOrigins`), with the loopback token, as any loopback page.

2. **One canonical origin: `http://127.0.0.1:<port>`.** `localhost` and `[::1]` are other origins to a browser: another storage (another pairing) and another install. A page request (GET or HEAD, not `/ws` or `/health`) on loopback whose Host is `localhost` or `[::1]` is redirected (308) to `127.0.0.1` on the bound port, path and query kept; the browser keeps the fragment, so a host link typed with `localhost` still pairs. `/ws` and `/health` answer on all three names, as before (the dev server's page is on `localhost:4517` and opens `ws://127.0.0.1`).
   - Why `127.0.0.1` and not `localhost`: it is what `nod serve` binds and prints, it needs no name resolution (`localhost` may resolve to `::1` first, where nothing listens), and a page on `http://localhost:<port>` could be served by another program bound to `[::1]:<port>`. So only `http://127.0.0.1:<port>` is an allowed origin, never `http://localhost:<port>`.

3. **The Host check comes first, on HTTP and WebSocket alike** (canvas ADR 0001, ADR 0005 §1, unchanged in kind): before the URL is parsed, a request is answered only when its Host names `127.0.0.1`, `localhost` or `[::1]` with no forwarding header (the loopback side) or the one `--allow-host` name (the named side); everything else gets 421. A DNS-rebinding page names its own host (`evil.example.test`, `127.0.0.1.example.test`, `localhost.example.test`), so it gets nothing: no page, no `/health`, no socket. A trailing dot (`localhost.`) and a number written another way (`2130706433`, `0x7f000001`) are refused as written; a browser normalizes the real loopback forms before it sends them. Serving a page on loopback makes this check what keeps a rebinding page from reading the app (and with it, nothing: the token is not in the page, but the check is the rule).

4. **Pairing is unchanged in kind**: the host link `http://127.0.0.1:<port>/#host=ws://127.0.0.1:<port>&token=<token>` (the route may come first, ADR 0005), the token kept in that origin's localStorage, the fragment replaced in the history entry right away (`takePairing`), so it does not stay in the address bar or under Back. An installed app shares the origin's storage, so it is paired too, and stays paired across restarts (the token is stable on disk) and updates (same origin). Not covered: a browser's own history database may record the visited address with its fragment before the page replaces it; that was true of the hosted UI as well. A different `--port` is a different origin and pairs once more.

5. **What `nod serve` prints.**
   - A release: the app's host link is the link ("open the dashboard"). `--open` opens it.
   - A checkout: the Vite dev server's link, as before (the dev server is where the code changes), and, when `dist/web` exists, the built app's link under it.
   - `--web-url <url>` (or `NOD_WEB_URL`) means what it said: the web app the printed link opens. Given, it replaces the app's link as the main one (the app is still served, and its link printed under it); its origin is let in on loopback. The hosted UI of the CLI's channel (`src/server/web-url.ts`) stays let in without the flag, for pairings made before this ADR and for deep links.

6. **The hosted UI stays for deep links, and forwards them to this machine's app** (extends ADR 0005 §7, same shape). A link in a PR comment opens `ui.nod.frebreco.de/#/pr/…`, which is no longer paired on a desktop. So:
   - **Where it forwards.** The record `nod.forward` (`lib/forward.ts`) now holds either a named host (`https://<name[:port]>`, the phone's) or this machine's app (`http://127.0.0.1:<port>`, exactly that: no other loopback name, no `https`). A hosted page that is **not paired** and remembers one offers "Open in the nod app" / "Open on `<name>`" with the route rebuilt from the parsed link (`forwardUrl`), never the raw fragment, never a token. One tap per link, as for the phone.
   - **The default.** The hosted page can only know the local port from what it remembered; with nothing remembered, the hosted UI (its origin only, not a dev server's page) offers the app on the default port, `http://127.0.0.1:4518`, next to the steps to start `nod serve`. An attacker gains nothing from that offer: the target is a fixed loopback address the page chose, not one a link names, and it carries no token. On a phone, loopback is the phone; a page there could only ask for a passphrase the way any link could, and a phone that remembers its named host never sees this offer.
   - **Learning another port.** The local app's avatar menu offers "Open links from GitHub here" when it runs on another port than 4518: `#/forward?to=http://127.0.0.1:<port>` on the hosted UI of the CLI's channel, with the same confirmation, the same default (not to remember), the same arming delay and the same frame refusal as ADR 0005 §7. The page that offers it is the app itself: a page whose pairing is `ws://<its own host>` on `127.0.0.1`.
   - **What is paired wins**, unchanged: a hosted page paired with loopback (an older pairing) shows the link where it is.
   - The page that is the app does not forward to itself.

7. **The service worker** (hand-written, `src/web/sw.ts`, no dependency) makes the installed app open without the server.
   - **Registered only by a page `nod serve` served**: a production build on a page that is not the hosted UI's origin (loopback, or the named host). Not on the hosted UI (its page follows its channel, not a server; a worker there would pin an old shell under a deep link), not on the Vite dev server. Scope `/`, the script `/sw.js` (`no-cache`).
   - **The cache is keyed by the build**: `nod-shell-<build id>`, the build id a hash of the build's files computed at build time (a small Vite plugin in `vite.config.ts`, which also writes it into `index.html` as `<meta name="nod-build">` and lists the files the worker precaches). A new `nod serve`, newer or older, serves a `sw.js` with another id, so the browser installs it on the next load; it calls `skipWaiting()` and `clients.claim()`, deletes every other `nod-shell-*` cache, and tells the open pages its build: a page whose own build differs reloads once (`shouldReload`), so no old shell is stuck after an update or a downgrade. After a reconnect the page asks the browser to check for a new worker.
   - **What it answers**: only same-origin GETs, and never `/ws`, `/health` or a request with `token` in its query. Navigations go to the network first and fall back to the cached shell when the network fails or a proxy answers 5xx (the named host's `tailscale serve` with nothing behind it). `/assets/` (hashed, immutable) come from the cache first. Everything else (the manifest, icons) network first, cache second. The worker writes nothing at run time: the cache holds exactly the build's files, fetched with `cache: "reload"` at install.
   - **The token never reaches it**: it rides in the fragment, which is not part of a request, and the socket is not a fetch; the query rule is a second guard.
   - With the server down, the app opens from the cache and shows **"nod serve isn't running"** with the command to start it and that `nod service install` (#52) keeps it running; it retries quietly with the usual backoff (0.5 s doubling to 10 s, and at once when the window becomes visible) and turns into the dashboard by itself.

8. **`nod service install|uninstall|status`** (#52) runs `nod serve` in the background: a systemd user unit on Linux (`~/.config/systemd/user/nod.service`), a LaunchAgent on macOS (`~/Library/LaunchAgents/de.frebreco.nod.plist`), Windows later. It runs the same nod that installed it, with the flags given, restarts it on failure, and captures `PATH` so it finds `gh` and `git`. A service is what makes "the app" true: a window that is always there needs a server that is always there.

9. **Updates take a click** (#53, #54). The server checks GitHub Releases of `FreshlyBrewedCode/nod` about every 10 minutes (unauthenticated, conditional requests) and on "Check now"; an update shows as an indicator at the top level of the UI and leads to Settings → Server, with the release notes (limited markdown, no HTML) and an **Update** button. **Installing always takes a click**: it is code that will hold the signing key, so nothing installs on its own. The server runs the install for the package manager it was installed with (npm, bun, …; unknown: settings shows the command), and the service restarts it; the app reconnects, and the service worker brings the new shell (7).
   - **Channel**: stable or next, in settings; switching is the same update flow to that dist-tag. The UI follows the server, so it follows the channel without a step of its own.

10. **The badge.** n = my tier 1 rows across all repos (`badgeCount` in `src/shared/attention.ts`, the repo filter does not narrow it): `navigator.setAppBadge(n)` where the browser has it, cleared at 0 (`clearAppBadge`), and the tab title `(n) nod` always (`nod` at 0, and while there is no snapshot). A per-viewer switch in Settings → App turns the icon badge off (`nod.badge`); the title stays. No push: there is no backend to send one, so the badge changes only while the app runs (minimized counts). Notifications for new tier 1 rows are a follow-up.

11. **Install.** Where the browser fires `beforeinstallprompt` (Chromium), the avatar menu and Settings → App offer a quiet "Install app"; installed, settings says so; elsewhere it says how this browser installs a site (Safari: File → Add to Dock, or Share → Add to Home Screen; Firefox: not at all, use Chrome, Edge or Safari). A page that is not the app (the hosted UI, the dev server) points at the app's address instead.

12. **Machine-changing actions happen only on this machine's side.** Installing an update, switching the channel and setting up the service change what runs on the machine; they are offered and accepted only on a loopback connection (`Side` in `src/server/signer.ts`, `Client.side`), never from the named host's page, whose UI does not show them (#54).

## Consequences

- A release's first contact is a link to `127.0.0.1`: no permission prompt, no channel to match, and the page can be installed. The hosted UI becomes a landing for links and the docs of how to start.
- `nod serve` serves files on loopback now; the Host check (3) and the static-file rules (1) are what guard it, both tested (`server.test.ts`, `static-files.test.ts`).
- A paired app has the stable token in its origin's storage, as the hosted UI had; nothing new is stored.
- An installed app opened while nothing runs shows a calm page instead of an error; once a service runs it (8), that page is rare.
- The badge counts only while a window is open; a closed app shows the last count the OS kept or none.
- What only real devices confirm: the install and the badge on macOS (Chrome, Edge, Safari's Add to Dock), Windows, Android Chrome through the named host, iOS home-screen apps (which have no badge for a site without notifications permission), and the service worker taking over after an update in each.
