# 0005: Another device reaches `nod serve` through one named host, same origin

Status: accepted (2026-11-21). Replaces the concept's "It talks to `nod serve` over loopback" (Architecture, Web app) and extends canvas ADR 0001's host-link guards as `src/server/server.ts` applies them. Evidence: [finding 04](../findings/04-phone-reach.md). Epic #30.

## Context

A phone cannot reach `nod serve`: it binds `127.0.0.1`, its Host check allows loopback names only, and the web client refuses any socket that is not loopback. The epic wants a phone on a private network, first a tailnet with `tailscale serve` in front (TLS, so `wss`), to read a brief and sign.

Finding 04 compared two shapes. **A**, the hosted UI opening `wss://<machine>.<tailnet>.ts.net` from `ui.nod.frebreco.de`, is blocked by Chrome's Local Network Access unless the user grants a permission whose prompt reads "connect to any device on your local network", and nobody knows what Android Chrome or Safari do. **B**, `nod serve` serving the web app itself on the tailnet name, is same-origin and needs no permission anywhere. B also lets the client keep a tight rule: a page may pair with loopback, or with the very https host that served it.

This changes the threat model: the pairing token and the passphrase now cross a network, and the server answers to a name that is not loopback.

## Decision

1. **Same origin, one named host.** `nod serve --allow-host <name[:port]>` (`src/shared/named-host.ts`) names the TLS proxy in front of the loopback port, e.g. `tailscale serve --bg --https=8445 http://127.0.0.1:4518` and `--allow-host <machine>.<tailnet>.ts.net:8445`.
   - Exactly one name. It is a DNS name with a domain: no IP literal (a certificate names a host), no loopback name, no wildcard, no scheme or path.
   - The server keeps binding `127.0.0.1`. Only the proxy, and local processes, reach it.
   - On that name, and only there, it serves the built web app (`src/server/static-files.ts`): no path out of the root, `index.html` for every other path, and no framing (`X-Frame-Options: DENY`, `frame-ancestors 'none'`), no sniffing, no referrer. Loopback still serves no page.
   - The Host check allows loopback and that name, nothing else. The origin allow-list is per side: a request whose Host is the named host may come only from `https://<name[:port]>`; a loopback request only from the hosted UI and the dev server, as before. So with the flag, the named side's allow-list is exactly the named origin. A request with no `Origin` at all is not a browser page (a script, a test) and is let in on either side with that side's token, as it always was on loopback.
   - **A proxied request is never loopback.** `tailscale serve` picks its handler by SNI and forwards the client's own `Host`, so a tailnet client that sends `Host: 127.0.0.1` would otherwise land on the loopback side, where no `Origin` is needed and the loopback token (in terminal scrollback, and in the hosted UI's storage) opens the socket. It also sets `X-Forwarded-For`, `-Host` and `-Proto` on every request it forwards, replacing what the client sent, and a client cannot remove them (finding 04, row 8). So a request carrying any of them, or `Forwarded`, gets the named side if its Host is the named host and 421 otherwise, with or without the flag. The loopback side is therefore: a direct connection to `127.0.0.1` that names a loopback host and carries no forwarding header. A program on this machine that sends a forwarding header and the named Host gets the named side; that is fine, it could reach loopback anyway and still needs the remote token. Another proxy must do what `tailscale serve` does (pass the client's Host, always set `X-Forwarded-For`); only `tailscale serve` is tested.
   - The Host is checked before the URL is parsed, and the server runs with `development: false` and an error handler that answers a bare 500: a malformed Host (`[x`, `name%zz`) gets 421, never Bun's error page with paths and source lines.
   - Without the flag, nothing changes; a test proves it.
   - **Not now: a `Tailscale-User-Login` check.** `tailscale serve` adds it for tailnet users, and comparing it with the `gh` login's owner would keep other people on the tailnet out. But any local process can send the header straight to the loopback port, tagged devices have none, and Funnel requests have none. It guards against other tailnet users only, who also need the token. It is the first candidate for a later addition, behind the same flag.
   - **Not now: several names.** One phone on one tailnet is the epic's case. A list would multiply the origins a token opens for no user who has asked for it.

2. **A token per side.** The named host has its own pairing token, separate from the loopback one and stored next to it: `$XDG_CONFIG_HOME/nod/serve-token-remote`, or `<--token-file>-remote` when `--token-file` is given, so tests and experiments never touch the real one. A socket is let in only with its side's token: the loopback token does not open the named host, and the remote token does not open loopback (`CLOSE_BAD_TOKEN` either way). The side is the Host header's, and Host, origin and token must all agree.
   - Why: a lost phone is unpaired by renewing its token, without unpairing the desktop. `--new-remote-token` renews only the named host's token; `--new-token` renews both, as it always meant "every paired browser pairs again".
   - The remote token lives as long as the loopback one does. A shorter life (a phone re-pairs every week) is left out: it adds a clock to pairing and nobody has asked for it; renewing is one flag and one QR scan.
   - Not per device: one token per side is enough to unpair "the phone". Per-device tokens would need a registry of devices, and a UI to list and revoke them, for a case (two phones) the epic does not have.

3. **The unlock window is per side.** Unlocking on a loopback connection does not let a named-host connection sign, and the other way round; locking ends only that side's window. Each client is told its own side's lock state (`signer` in `welcome` and every `signer` push), so the phone shows "locked" while the desktop is unlocked. The key itself is one: the decrypted key stays in memory while either side is unlocked and is dropped when both are locked; a second unlock checks the passphrase again and keeps the key it has. `UnlockWindow` (`src/server/signer.ts`) holds one window per side, not per socket: two tabs on the desktop share a window, as today.
   - Why: once two devices are paired, a window opened at the desk must not also arm the phone in a pocket, and a phone left unlocked on a table must not arm a page on the desktop. Per side is the smallest rule that gives that, and it matches the token classes, so it is the same boundary twice.
   - Not per socket: a reload, or a second tab, would lock the user out; and the signer would have to know about sockets.
   - **One unlock at a time per side.** A wrong passphrase waits a second before it fails, so guessing through the socket stays at about one a second per side. Each side has at most one unlock being checked; another one from the same side is refused at once with `unlock-pending`. The key file's unlocks still take turns (each costs scrypt's memory), but the wait after a wrong one is outside that turn. So wrong guesses on the phone hold up an unlock at the desk by one scrypt run at most, not by a second per guess. Rejected: a queue per side (unbounded, and a second per queued guess); one delay for everyone (the starvation this replaces).

4. **The served web app is the CLI's own build.** The npm package ships it (`scripts/build-release.ts` builds it with base `/` into the package's `web/`, and the smoke test checks it is there and loadable). The default `--web-dir` is the package's `web/`, and in a checkout `dist/web`; when it is missing, `nod serve --allow-host` stops with "run `bun run build`". So the page on the named host always speaks the CLI's protocol, whatever channel the hosted UI is on. The hosted UI is unchanged: it stays the desktop's, paired over loopback, following the CLI's release channel (`src/server/web-url.ts`).

5. **The device link, as a QR code.** With `--allow-host`, and only then, `nod serve` prints a second link for the other device and the same link as a QR code in the terminal, with one line: scan it, do not send it through a chat. A link sent to yourself stays in that service's history, and in any synced clipboard, with a token that does not expire; a QR code never leaves the two screens. The encoder is [`uqr`](https://github.com/unjs/uqr), a dependency of `nod serve` only: zero dependencies of its own, one small ES module, maintained by the unjs project, and it renders to Unicode half blocks. Writing an encoder (Reed–Solomon, masks, version tables) would be several hundred lines of code nobody reviews for a feature whose failure mode is a code that does not scan. The kit stays dependency-free; `uqr` is imported only by `src/server/qr.ts`, and only when the flag is given.

6. **No plain-http access from another device, ever.** TLS comes from the proxy. The named origin is `https://` only, the client accepts `wss://` only to the https host that served it, and `ws://` stays loopback-only. A LAN address over `http://` would send the token and the passphrase in clear over Wi-Fi.
   - **The named host's page pairs only with itself.** On a phone, loopback is the phone: a crafted link `https://<name>/#host=ws://127.0.0.1:4518&token=…` would otherwise replace the real pairing and hand the passphrase to an app on the phone listening there. So a page may pair with loopback only when it is the hosted UI (the origin of `STABLE_WEB_URL` in `src/server/web-url.ts`, which the client imports, so there is no second list to drift; both channels share that origin) or a page on a loopback host (the dev server, a preview). Every other page pairs only with `wss://<its own host>`, and a stored pairing that breaks the rule is dropped on load. It fails closed: the named host's page is covered whatever build it runs, without the server marking it. The cost: a web app on another https origin (`--web-url`) cannot pair with loopback.
   - Rejected: the server marking its page (a meta tag or header): it fails open when the mark is missing; a build flag: a checkout's `dist/web` would not have it.

7. **Deep links on the phone: built** (`src/web/lib/forward.ts`, `components/forward.tsx`; amended 2026-11-22). A GitHub notification opens the hosted UI's `#/pr/<owner>/<repo>/<n>`, which is not paired on the phone. The hosted page cannot read the named host's storage, and it cannot even reach it (Local Network Access, above). So the hosted origin has to be told where this browser's nod is, and that is the risk: whoever can set that remembered host can forward the user to a page that asks for the passphrase. As built:
   - **How the hosted origin learns the host.** Only from a top-level navigation to `https://ui.nod.frebreco.de[/next]/#/forward?to=https://<name[:port]>`, which the named host's page starts from "Open links from GitHub here" in its avatar menu. The item is a plain link carrying the page's own origin and nothing else (`forwardSetupUrl`): never the token. It goes to the hosted UI of the CLI's channel (a release: the stable root; a pre-release or a checkout: `/next`); both channels share the origin, so the one record serves links to either. The menu item shows only on a page that pairs with its own https host, never on the hosted UI or loopback, so a desktop sees nothing new.
   - **The rule for the host** is `--allow-host`'s, moved to `src/shared/named-host.ts` so the web bundle imports it without server code. It now also refuses a name whose last label is a number or `0x…` (`0x7f.1`, `laptop.1`): a browser parses such a name as an IPv4 address. On the hosted side the value must be written exactly as an origin, `https://<name[:port]>` with at most a trailing `/`: no userinfo, path, query, fragment, backslash, percent sign or whitespace, before the name is parsed at all; a port 443 and upper case are normalized away. Internationalized labels (`xn--`) are refused: the confirmation shows the name as written, a homograph in punycode is not something to ask a user to compare, and a tailnet name is ASCII. A `to` given twice is no host. The stored record is checked again on every load and dropped when it fails.
   - **What the user confirms.** Nothing is stored on arrival. The hosted page cannot tell a real request from a crafted link, so the confirmation is the guard: a full page that shows the whole host in large monospace type (`https://` in grey, the name and port in full, wrapped, never cut), says what remembering means, and that anyone can make such a link and a page there could ask for the passphrase ("Remember it only if you tapped … a moment ago, and the address is your machine's"). **The default is not to remember**: "Don't remember" is the prominent button and has the focus, so Enter leaves; "Remember this address" is the outlined one; leaving the page stores nothing. A host that replaces another names both. A refused host gets a page that says so, shows what was given as text, and has no remember button. "Remember" stores `{ to, since }` under `nod.forward` in the hosted origin's localStorage; it does not expire, like the pairing. The host line breaks only after a dot or before the port: a hyphen stays glued to the character after it (`hostParts`), and only a label wider than the whole line breaks anywhere.
   - **Three rules against a swapped host or a stolen tap** (amended after a security review, 2026-11-22):
     - **The confirmation is keyed on `to`, and the page after it shows what is stored.** An opener (or anything else) can change the fragment of a page that is already open; the page re-reads `to` on `hashchange`. So `ForwardConfirm` is mounted with `key={to}`: another host is another page, nothing tapped, and its button is not armed. The finished page ("Links from GitHub open your nod at") shows the host read back from storage, and its "Back to your nod" goes there: never the fragment's host, which may have changed after the tap.
     - **Armed after a second of being visible.** "Remember this address" is disabled (dimmed, the same label) until the page has been visible for `ARM_MS` (1 s) in one go: since it mounted, since `to` changed, or since it was last hidden or restored from the back-forward cache (`lib/guard.ts`, pure and tested with the caller's clock; `hooks/use-armed.ts` reads `document.visibilityState`). A double-click trick that lands a second tap where the button appears, a swap just before the tap, and a page opened in the background all meet a disabled button. "Don't remember" is never delayed. Rejected: counting visible time across hidden stretches (a page can be shown for a moment at a time); a longer delay (a real user reads the host for longer anyway, and a calm second is enough to defeat tap timing).
     - **The web app refuses to run inside another page.** When `window.top !== window.self` (`isFramed`), the whole app shows one bare page, "nod does not run inside another page", before the connection or the fragment is looked at: nothing pairs, nothing is remembered, no passphrase field. The whole app, not just the confirmation: the dashboard has the passphrase field too, and framing nod is never wanted. The header would be the better guard, but the hosted UI is on GitHub Pages, which sends no `X-Frame-Options` or CSP and takes no header config, and a `<meta>` CSP cannot carry `frame-ancestors`; so the script check is what the hosted UI has. A frame with `sandbox` that blocks scripts shows nothing at all. The named host's page also refuses framing by header (§1), and the dev server and `vite preview` send the same headers.
   - `scripts/check-phone.ts` keeps these: the fragment changed after the tap and just before it, a page loaded hidden, a cross-site frame of the hosted origin (played by routing, without headers as GitHub Pages serves it), and where a long hyphenated host breaks.
   - **What the hosted page shows before it forwards.** A deep link on a hosted page that is not paired and remembers a host shows the usual "Opened from a link" banner and, instead of the pairing steps, "Open it in your nod", the host spelled out the same way, one button **"Open on `<name[:port]>`"**, "Forget this address", and the PR on GitHub. The button is a plain link: a top-level navigation to `https://<name>/#/pr/<owner>/<repo>/<n>` rebuilt with `formatRoute` from the parsed route, never from the raw fragment, so a pairing after the route (`?host=…&token=…`) is not carried and nothing in the route can leave the host (`#` comes first, every part is encoded and restricted). No silent forward: one tap per link keeps the remembered name in front of the user every time, which is what makes a wrongly remembered host noticeable. The plain unpaired page (`#/`) offers "Open your nod" the same way, so the host can be forgotten without a link.
   - **What is paired wins.** A hosted page with a pairing never forwards, whatever its socket does (connecting, closed, refused): a desktop paired with loopback sees today's landing even if it remembers a host. The confirmation still shows when a `#/forward` link is opened there, and says that links keep opening here while the browser is paired.
   - **Where it forwards from.** Only the pages that may pair with loopback (`pairsWithLoopback`: the hosted UI and pages on this machine) remember a host and forward. The named host's page ignores `#/forward` (it shows its list), so a crafted link cannot chain one named host to another.
   - **On the named host.** The route opens the existing landing. Not paired there, it remembers the link (`rememberLink`) and shows the unpaired landing, worded for that page: start `nod serve --allow-host <this host>` and scan the QR code with this device; the device link then lands on the PR.
   - **A home-screen app** (`display: standalone`, see the manifest) has no address bar, and on iOS a storage of its own. Its unpaired pages add a field to paste the link `nod serve` printed for this device (`pastedHostLink`): accepted only when it is a link to this very origin that pairs it, then handed to the usual fragment pairing, which drops it again.
   - **Rejected:** remembering on pairing without a confirmation (any page can navigate to the hosted UI with a crafted value); a confirmation whose default is "remember"; allowing only `*.ts.net` (Funnel makes such names public, so it proves nothing); `registerProtocolHandler` (not on Android Chrome or iOS Safari); a silent forward (a planted host would never be seen again); forwarding from a paired page ("open on the phone's nod" from a desktop is not a case); a forward that keeps the raw fragment.
   - **Not proven without a real phone** (the browser check stands the hosted origin in by routing it, see finding 04's list): that iOS Safari and Android Chrome open the forward with no prompt from the real hosted origin, and how an iOS home-screen app hands a navigation to another origin (the docs say to tap "Open links from GitHub here" in Safari).

8. **No config file.** `nod serve` has no config mechanism today; the flag is repeated. A config entry for it waits for the first config file.

## Consequences

- Who can try to connect grows from the machine's processes to every device and user the tailnet's ACLs let reach that port, shared nodes included. The token is still what lets a client in; the tailnet only narrows who can try. `tailscale serve`, not Funnel: Funnel would put the name on the internet, and nothing here guards against that beyond the token.
- The passphrase travels under TLS from the phone to `tailscaled`, inside WireGuard, and in plain HTTP only on the machine's loopback, as before. It is never stored on the phone.
- The remote token sits in the named origin's localStorage on the phone. A lost phone that is still on the tailnet can open the socket until `--new-remote-token`, or until the phone leaves the tailnet; with a per-side window it cannot sign in a window opened at the desk.
- `tailscale serve`'s HTTPS certificate puts the machine and tailnet names in a public certificate log. The docs say so.
- The package grows by the built web app (about 860 KB in 15 files) and one dependency.
- The deep-link forward is opt-in per browser and one tap per link: a GitHub notification on the phone still lands on the hosted UI first, and a phone that never confirmed a host gets today's pairing page there.
- Only `tailscale serve`'s forwarding headers were checked (finding 04, row 8); a proxy that does not set them would let a loopback Host through to the loopback side.
- What only a real phone can confirm (Android "secure DNS" and MagicDNS, iOS Safari's local network rules, a frozen tab) is listed in finding 04.
